# Inkcast: a Keycloak realm import applied before its client-secret Secret exists

*Research date: 2026-10-29, for issue #343 (found by the review of PR #336, concern C6). Sources:*
- *the lab: OpenShift Local 4.22.14, Red Hat build of Keycloak operator `rhbk-operator.v26.6.7-opr.1` in namespace `keycloak`, server `Keycloak 26.6.7.redhat-00003` (`kc.sh --version` in `keycloak-0`), CR `keycloak`, one instance;*
- *the operator's source at the upstream tag the build carries, `keycloak/keycloak` 26.6.7, `operator/src/main/java/org/keycloak/operator/controllers/`: `KeycloakRealmImportJobDependentResource.java`, `KeycloakRealmImportController.java`, `KeycloakRealmImportSecretDependentResource.java`, read on that date;*
- *Keycloak's import strategy at the same tag, `model/storage-services/src/main/java/org/keycloak/exportimport/util/ImportUtils.java`;*
- *Kubernetes at tag v1.35.0: `pkg/kubelet/kubelet_pods.go` (how a Secret-backed environment entry is resolved), `pkg/controller/job/job_controller.go` (what counts as a failed pod) and `pkg/apis/batch/v1/defaults.go` (the default pod replacement policy);*
- *this repository: `deploy/kustomize/shared/keycloak-realms`, `scripts/gen-realm-imports.py`, `deploy/kustomize/components/env-secrets`.*

*Every number below is from a command run on the lab on that date; the raw outputs are in §5. No Secret value appears: the only Secret the experiment created held the literal `measure-343-not-a-secret`.*

## 1. How the imports reference their Secret (this repository)

- `deploy/kustomize/shared/keycloak-realms/realm-inkcast-<side>.yaml`, generated by `scripts/gen-realm-imports.py` from `deploy/keycloak/realm-inkcast.json`: `spec.placeholders` maps `KC_INKCAST_CLIENT_SECRET` and `KC_INKCAST_SYNC_SECRET` to `{secret: {name: inkcast-<side>-realm, key: identity-client-secret | sync-client-secret}}` (`realm-inkcast-staging.yaml:15-23`; the map is `PLACEHOLDERS` at `scripts/gen-realm-imports.py:44-45`). The realm text keeps `${KC_INKCAST_CLIENT_SECRET}` and `${KC_INKCAST_SYNC_SECRET}` as the two clients' `secret`.
- `deploy/kustomize/components/env-secrets` (PR #336, #323): the init container `env-secrets` of OpenFGA's pod in `inkcast-<side>` creates `keycloak/inkcast-<side>-realm` with those two keys, and the same values in `inkcast-<side>/inkcast-secrets`. Production's pod has no release yet (placeholder digest), so `inkcast-prod-realm` does not exist and its import waits.

## 2. What the operator does with a placeholder (source, tag 26.6.7)

`KeycloakRealmImportJobDependentResource.java`:

- line 68: the Job is built from the Keycloak CR's StatefulSet, `ContextUtils.getCurrentStatefulSet(context).orElseThrow()`; lines 72-74: its pod template is a copy of the server's, `existingDeployment.getSpec().getTemplate()`.
- lines 105-119: for every placeholder, an environment variable is added to the Job's container: `.withName(secret.getKey()).withNewValueFrom().withNewSecretKeyRef().withName(…getSecret().getName()).withKey(…getSecret().getKey()).withOptional(false)`. `optional: false` (line 114) is why the kubelet refuses to start the container while the Secret is missing and keeps retrying, instead of starting it with the variable unset.
- line 158: the container runs `kc.sh --verbose import --file=/mnt/realm-import/<realm>-realm.json --override=false`; `kc.sh import` resolves `${VAR}` in the realm text from the process environment. The Secret must hold the intended values before the container starts. A wrong value is imported as it is. A later change to the Secret does not repair the realm: `--override=false` is the strategy `IGNORE_EXISTING`, and `ImportUtils.importRealm` skips a realm that exists with `Realm '%s' already exists. Import skipped` (`ImportUtils.java:105-114`).
- line 125: `restartPolicy: Never`; lines 130-141: the Job spec sets only the template, so Kubernetes' defaults apply (`backoffLimit: 6`, no `activeDeadlineSeconds`), as the lab's Job shows. A pod in `CreateContainerConfigError` is `Pending`, not `Failed`. While it stays `Pending` and nobody deletes it, it uses no Job retry, and the lab's Job showed `failed` empty after 4 min 25 s. Deleting or evicting that pod can count as a failure: `isPodFailed` (`job_controller.go:2011-2020` at v1.35.0) counts a pod with a `deletionTimestamp` that has not succeeded, under the default `podReplacementPolicy: TerminatingOrFailed` (`defaults.go:62-69`). Repeated deletion of the waiting pod can therefore spend the 6 retries before the Secret arrives, and the import then reports `HasErrors "Import Job failed"`.
- lines 171-173: the probes are removed ("we are not really starting the server").

`KeycloakRealmImportSecretDependentResource.java`, lines 25-39 and 42: the realm JSON itself goes into a Secret named `<keycloakCRName>-<realm>-realm` (`keycloak-zz-measure-343-realm` in the experiment), mounted at `/mnt/realm-import/`; it is owned by the import and garbage-collected with it.

`KeycloakRealmImportController.java`:

- lines 63-68: the reconciler reads the Job, the StatefulSet and the Keycloak CR; it never writes the CR or the StatefulSet. The CR must exist (`.require()`, line 68). Lines 74-76: the Job and realm Secret are created only when the StatefulSet has a ready replica. Until then the status is different from the measured waiting state (lines 111-123): no StatefulSet gives `HasErrors "No existing Deployment found, waiting for it to be created"`, and a StatefulSet with no ready replica gives `Started "Import Job will start soon"` with `HasErrors "Deployment not yet ready"`. The reconciler retries, so the Job is created when a replica is ready. This case was not driven.
- lines 93-95: while not done, it reconciles again after `Constants.RETRY_DURATION` (the operator log shows a pass every 10 s, "Job already executed - not recreating", "Job running").
- lines 126-145: the status is read from the Job: `succeeded > 0` → `Done` (line 135, the authors' comment: "no need to restart Keycloak as we're only importing new realms and are not overwriting existing realms"); `failed > 0` → `HasErrors "Import Job failed"`; otherwise `Started "Import Job running"`. A missing Secret is therefore reported as a running Job, not as an error.

## 3. The experiment

A throwaway realm, `zz-measure-343`, with one confidential client whose secret is `${KC_MEASURE_343}`; the placeholder reads key `client-secret` of Secret `zz-measure-343-realm`, which did not exist when the import was applied. The Secret's value was the literal `measure-343-not-a-secret`.

```yaml
apiVersion: k8s.keycloak.org/v2beta1
kind: KeycloakRealmImport
metadata:
  name: zz-measure-343
  namespace: keycloak
  labels:
    inkcast.io/measurement: "343"
spec:
  keycloakCRName: keycloak
  placeholders:
    KC_MEASURE_343:
      secret:
        name: zz-measure-343-realm
        key: client-secret
  realm:
    realm: zz-measure-343
    displayName: Throwaway realm for measurement 343
    enabled: true
    clients:
      - clientId: zz-measure-343-client
        enabled: true
        publicClient: false
        clientAuthenticatorType: client-secret
        secret: ${KC_MEASURE_343}
        standardFlowEnabled: true
        redirectUris:
          - https://example.invalid/callback
```

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: zz-measure-343-realm
  namespace: keycloak
  labels:
    inkcast.io/measurement: "343"
type: Opaque
stringData:
  client-secret: measure-343-not-a-secret
```

Steps, each a script run on the lab over SSH (`oc` through `crc oc-env`):

1. `check.sh` (the `/inkcast-crc` health check): 9 FAIL lines, all pre-existing (`inkcast-prod` not promoted and its import waiting).
2. Phase 1: record `keycloak-0`, the StatefulSet and the CR; `oc apply` the import; every 30 s for 3.5 min read the import's conditions (`-o jsonpath='{.status.conditions}'`), the Job's `active/succeeded/failed`, the pod's container state; then the events, the Job's env entry for the placeholder, and the server state again.
3. Phase 2: `oc apply` the Secret; every 5 s read the same until `Done=True`; then the full timeline (Secret `creationTimestamp`, container `startedAt`/`finishedAt`, Job `completionTime`), the Job's log, the realm's discovery document through the Route with the cluster's own CA (as `check.sh` probes), and the server state.
4. Phase 3, in the recorded order. At 08:37:39 `oc delete` the import (its Job, pod and realm-file Secret follow by owner reference) and the throwaway Secret. At 08:37:59 prove that each is gone. At 08:38:40, inside `keycloak-0`, run `kcadm.sh` against `https://keycloak.apps-crc.testing` with a PKCS12 truststore built by `keytool` from the pod's own `/mnt/certificates/tls.crt` and the credentials from the pod's `KC_BOOTSTRAP_ADMIN_*` environment, never printed. Compare the imported client's secret with the placeholder value, delete the realm, and remove the CLI's token file and truststore. At 08:38:57 prove that the realm answers 404. Then run `check.sh` again.

## 6. Not measured

- A Secret that exists but lacks the key. The kubelet reports `CreateContainerConfigError` with the message `couldn't find key` (`kubelet_pods.go:894-921` at v1.35.0). The same waiting state is expected from the same `optional: false`, but it was not driven.
- A Secret that holds a wrong value. The realm is imported with that value, and a later change to the Secret does not repair it (`--override=false`, `ImportUtils.java:105-114`). Not driven.
- An import applied before the Keycloak CR exists, or before a replica of its StatefulSet is ready. The controller reports an error status until then and creates the Job when a replica is ready (`KeycloakRealmImportController.java:74-76` and `:111-123`). Not driven.
- A waiting pod that is deleted or evicted. It can count as a Job failure (`job_controller.go:2011-2020`), so repeated deletion can spend `backoffLimit` 6 before the Secret arrives. Not driven.
- `inkcast-prod` itself. The same completion is expected when a production promotion merges and env-secrets writes `inkcast-prod-realm` with both keys and the intended values, if Keycloak is ready and the Job has not failed. `check.sh` will show it (`realm import inkcast-prod` PASS, discovery 200).
- A pod watch (`oc get pods -w`) was started for the server pods; its custom columns came out empty (the watch-event wrapper nests the object), so the server's identity was read directly before, during and after each phase instead, as the outputs above show.
