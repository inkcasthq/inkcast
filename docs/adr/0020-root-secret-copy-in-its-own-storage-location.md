# ADR-0020: The root Secret's copy, an OADP Schedule into a storage location of its own

**Status:** accepted, 2026-11-04 (the owner: option A, with an in-cluster object store on the lab; the integrator: SeaweedFS as that store, once MinIO's images were found withdrawn; issue #436) · **Epic:** E3.F3.9 (the generated Secrets), with E7.F7.6 (disaster recovery)

## Context

Each lab environment's root Secret, `inkcast-secrets`, holds two values held nowhere else: `secret-key`, which seals every platform credential at rest (`libs/secrets/value.py`, `Sealer`) and derives the PKCE and nonce HMAC keys, and `fga-api-token`, OpenFGA's preshared key. From PR #423 the CronJob `inkcast-env-secrets` runs `inkcast env-secrets --repair-only`: it copies a value that one side of a pair still holds and never makes a new one, so a deleted `inkcast-secrets` fails the run, which names the two values as lost ([the runbook](../runbooks/env-secrets.md)).

The runbook's step 1 said "restore the Secret from a copy", and the repository made none. `inkcast backup` copies the SQLite file, and that file is useless without `secret-key`. Without a copy the remedy is a restart of OpenFGA's pod: its init container makes a new `secret-key`, every sealed credential becomes unreadable for good, in the database and in every SQLite backup, and every platform must be connected again by its owner.

Two rules bound the choice:

- A key kept where the data it decrypts is kept protects nothing. Percona's operator documentation on encrypted backups: when the key is lost or rotated the backup cannot be recovered, and a restore on another cluster needs the same key supplied from outside. A third-party guide on Rancher backups says the same.
- Restoring the copy must never overwrite a value the pods are running on: a new value cuts them off what they hold (the runbook, "A root value is lost").

## Decision

**An OADP (Red Hat's build of Velero) Schedule per environment copies the labelled root Secret, and nothing else, into a BackupStorageLocation of its own; the restore is Velero's, which never overwrites.**

- **The label.** `inkcast-secrets` carries `inkcast.io/root-secret: "true"`. `inkcast env-secrets` sets it when it creates the Secret and adds it, by the same merge patch it adds a missing key with, to a Secret that lacks it, in both of its modes (`src/inkcast/env_secrets.py`, `ROOT_SECRET_LABEL`): a label cuts no pod off anything. Every manifest that defines the Secret carries it too (the CI overlays' `secretGenerator`, `deploy/dev`, the ExternalSecret's template). `tests/test_root_secret_copy.py` keeps the code's label and the Schedules' selector equal.
- **The operator**, `deploy/kustomize/shared/oadp-operator`: OADP through OLM in `openshift-adp`, the namespace its documentation uses, pinned with `installPlanApproval: Manual` and `startingCSV` (1.6.2 on OpenShift Local 4.22), so an upgrade is a change in Git; `scripts/lab/root-secret-copy.sh` approves the one InstallPlan that carries that CSV.
- **The copy**, `deploy/kustomize/shared/oadp`: one DataProtectionApplication, Velero alone (`nodeAgent.enable: false`: no DaemonSet, no volume backups; `backupImages: false`: no registry), one BackupStorageLocation `root-secrets` with its own bucket `inkcast-root-secrets` and its own credential `cloud-credentials-root-secrets`. It is the default because the operator demands one of the locations it is given (measured on 1.6.2: without it the DPA stays `Reconciled=False`, "no default backupstoragelocations configured"); every Schedule names its location, so the default decides nothing for the copies. It does decide for anything else: while `root-secrets` is the only, and so the default, location on a cluster, never create a Velero Backup or Schedule there without `storageLocation`, or namespace data lands in the key's bucket (the runbook says so too). Production ships the data backups' location (E7.F7.6.S2) as the default beside this one, with `root-secrets` set to `default: false`, so nothing lands in the root Secrets' bucket by omission. Two Schedules, `inkcast-staging-root-secret` and `inkcast-prod-root-secret`: `includedResources: [secrets]`, the label selector, that environment's namespace, no cluster resource, no volume, daily at 03:47 UTC, `ttl` 90 days. The bound on the TTL is the oldest SQLite backup the key must open, `INKCAST_BACKUP_KEEP` days (14 in both environments; the test reads each environment's value); six times that leaves eleven weeks to notice a Schedule that stopped. The GDPR bound on backups does not apply: the Secret holds keys and no personal data.
- **The restore** (the runbook, step 1): a `Restore` of the latest backup limited to `secrets` carrying the label in the namespace. Velero's default `existingResourcePolicy: none` "will never overwrite data that already exists in your cluster", and "the same selector syntax works on restore". Then the CronJob's next run exits 0 and the sealed credentials read: `scripts/ops/root-secret-drill.sh` proves it, with a safety copy first, the comparison by SHA-256 only, and every stored credential unsealed inside the server's pod with the key it mounts (no endpoint or command unseals on demand).
- **Production** points the location at an off-cluster bucket encrypted with a KMS key (SSE-KMS: Velero stores a Secret as a manifest in its tarball, so the bucket's encryption and access policy are what protect it), with an IAM key for that bucket alone in `cloud-credentials-root-secrets`, made by the cloud's secrets process. The DPA's `config` block (`s3Url`, `s3ForcePathStyle`) is the lab's and goes.
- **The lab's stand-in**, `deploy/kustomize/shared/seaweedfs` with `shared/seaweedfs-admission` and `shared/seaweedfs-access`: SeaweedFS installed from its own Helm chart, `seaweedfs` 4.52.0 from the project's chart repository, pinned by version and by the tgz's SHA-256 in `scripts/versions.env`, read at its source (the project's public repository, `k8s/charts/seaweedfs` at tag 4.52, Apache-2.0; its `openshift-values.yaml` gives the restricted SCC's security contexts). The values file beside the kustomization sets, each line citing the chart: the all-in-one pod (`weed server` with master, volume, filer and the S3 gateway in one process; the separate master, volume, filer and gateway off, as the chart requires), one 2Gi claim, Recreate, S3 with `enableAuth` and `existingConfigSecret`, the bucket made by the chart's post-install hook (`createBuckets`), the chart's own NetworkPolicy with one extra rule admitting Velero's pods on the S3 port, the image by digest through `master.imageOverride` (the one image value that takes a digest: the chart's `image.*` values compose name:tag), and everything else the chart can start off (WebDAV, the admin UI, the Iceberg and Lance catalogs, telemetry, SFTP, COSI, the worker). What the chart does not do is the kustomization's: the namespace, and the Job `seaweedfs-setup` that generates the one identity's key pair (`velero`, allowed Read, Write and List on that bucket and nothing else) from the kernel's CSPRNG and writes it once as the identities file the chart mounts and once as Velero's credentials file, never printed and never on a command line, keeping what exists and copying a side that is absent, as env-secrets treats a pair; an admission policy limits that account to Opaque Secrets under those two names with no service-account annotation, so it can never make itself a token of Velero's account. The hop is plain HTTP in the cluster, as the repository's other in-cluster hops are (OpenFGA, Mailpit), with the bucket's access scoped by the key. The limit, stated once in the runbook: the store is in the same cluster as the data, so the copy survives a deleted Secret, not the loss of the cluster, and the claim is not encrypted. A switch of store is a change of the store's values (or chart) behind the same S3 BackupStorageLocation: the DPA, the Schedules and the restore stay as they are.

## Options considered

| Option | For | Against |
|---|---|---|
| **A. OADP (Velero) Schedule** of the labelled root Secret into a storage location of its own (chosen) | OpenShift's supported cluster backup, already named by the runbook. Non-destructive restore by default. Label selection on backup and restore. A DPA takes several locations, each with its own credential, so the key's location never shares a bucket with the data's. No Inkcast code beyond a label | Needs an S3-compatible object store; Velero stores the Secret as a manifest, so the bucket's own encryption and access policy protect it |
| B. External Secrets Operator `PushSecret` into a secrets manager (Vault/OpenBao, AWS Secrets Manager) | The manager becomes the key's home; `deletionPolicy` keeps the provider's copy by default; Inkcast already reads from these managers | Needs a secrets manager, which neither the lab nor production has today; an in-cluster Vault for this alone would be a lab-only stand-in |
| C. A sealed export by `inkcast env-secrets`, encrypted to an operator's public key | No new infrastructure; Vault's `operator init -pgp-keys` is the precedent | New cryptography and a new dependency in a central path, plus a private key someone must hold; it repeats what A gives without code |

| Store | Measured | Verdict |

| MinIO (the owner's first word) | Its repository is archived and its images cannot be pulled: `quay.io/minio/minio` and `docker.io/minio/minio` refuse every tag anonymously (`latest`, the 2024 and 2025 releases), from two networks; `dl.min.io`'s release binaries answer HTTP 410; the README says "THIS REPOSITORY IS NO LONGER MAINTAINED" and "distributed as source code only" (2025-10-23 per Chainguard). ## Consequences

- No Inkcast code beyond the label; the restore is Velero's. `tests/test_env_secrets.py` (`RootSecretLabel`) holds the label's cases; `tests/test_root_secret_copy.py` holds the manifests, the scripts and the runbook.
- The copies are Velero's tarballs of the Secret's manifest, one a day per environment, garbage-collected after 90 days; the bucket's encryption and access policy are the protection. On the lab the bucket is in the same cluster and its volume is not encrypted: the stand-in, not the standard.
- A Secret put back by hand, or made before the label existed, gets the label from the CronJob's next run (or the init container's), so the next copy holds it. Until the release that carries this change runs, `scripts/lab/root-secret-copy.sh` labels the existing Secrets by hand, which `inkcast env-secrets` then keeps.
- An OADP upgrade is a change to `subscription.yaml`, approved by the install script, and drilled before it is called done. A changed identities file on the lab takes a rollout restart of the store.
- `components/backup`'s note "store the key elsewhere" now names where: the runbook's step 1. E7.F7.6.S2's off-cluster copy of `inkcast-backups` goes to another location, never `root-secrets`.
- Measured on the lab on 2026-11-04 (OpenShift Local 4.22.14, OADP 1.6.2, SeaweedFS 4.52; `scripts/lab/root-secret-copy.sh`, whose run is in the pull request): the CSV `oadp-operator.v1.6.2` Succeeded from the approved InstallPlan; the setup Job wrote both Secrets and, run again, kept them "in agreement"; the location `root-secrets` reached `Available`; the backup `inkcast-staging-root-secret-20261104174654` Completed with 1 of 1 items within a second, expiring 90 days on, and the store listed its nine objects (`velero-backup.json`, the 831-byte tarball, the logs) in the bucket; the aws plugin's default `checksumAlgorithm` (CRC32) was accepted, so the location sets none. Two facts came from the lab and not from the sources: the operator demands a default location, and on this cluster `oc get backup` names CloudNativePG's `backups.postgresql.cnpg.io`, so the scripts and the runbook write `backups.velero.io` and `restores.velero.io` in full.
- Measured again on the lab the same day, the store from the chart (`seaweedfs` 4.52.0, the tgz's SHA-256 as pinned): the setup Job copied the identity into the chart's Secret from Velero's side ("from openshift-adp/cloud-credentials-root-secrets"), then kept the pair "in agreement" on the next run; the admission policy, probed with server-side dry runs as the setup account, refused a service-account-token Secret for Velero's account under the credential's name, an Opaque Secret under another name and the credential annotated for a service account, and admitted the Opaque credential under its own name (a fact of the API's order came with it: a Secret is validated before an admission policy sees it, so a token-type probe must carry the annotation the type requires); `helm upgrade --install` deployed release `seaweedfs` with `seaweedfs-all-in-one` rolled out and the chart's two policies in place; the location re-validated `Available` on the chart's Service; the backup `inkcast-staging-root-secret-20261104184825` Completed with 1 of 1 items and its nine objects listed in the new store's bucket. The first store's claim (`seaweedfs-data`, holding two test backups) and its identities Secret (`seaweedfs-s3-identities`) were left in place for the integrator; the chart's claim is `seaweedfs-all-in-one-data`.
